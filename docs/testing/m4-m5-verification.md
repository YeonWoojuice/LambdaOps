# M4·M5 검증 게이트 — 설계 제안, 사용자 승인 전

이 문서는 **앞으로 실행할 시험 기준의 초안**이다. M4·M5 구현, 테스트 통과 또는 AWS 배포 기록이 아니다. 기존 [M2·M3 검증 기준](m2-m3-verification.md)을 반복하지 않고 그 완료 증거를 선행 조건으로 사용한다. [M4 Notion 마일스톤](https://app.notion.com/p/3ea91c6807b18121b17cf3b7543f23d3)과 [M5 Notion 마일스톤](https://app.notion.com/p/3ea91c6807b18115904cf3fe839fae76)의 완료 기준을 유지한다.

| 단계 | 다음 단계로 넘기기 전 필요한 실제 증거 |
| --- | --- |
| M2 → M3 | 실제 지표와 Alarm 3종의 적용·`ALARM→OK` 전이. 코드·Terraform 검사만으로 통과시키지 않는다. |
| M3 → M4 | `ALARM→Incident` 대표 1건, 중복·`OK`·실패 재처리, 인증된 실제 Detail 조회. 직접 넣은 `DEMO` Incident 조회는 자동 접수 경로의 증거가 아니다. |
| M4 → M5 | 원인을 알고 주입한 첫 장애에서 근거 기반 RCA를 검증하고, 이후 앱·인프라·DB 분류에 관한 기존 M4 완료 기준을 확인한다. 분석 보고서에는 실제로 확인 가능한 근거가 필요하다. |
| M5 완료 | 시험 환경에서 승인된 단일 작업에 대해 권장→승인→실행→사후 확인이 동작하고, 거절·실패·중복 요청도 안전하게 처리한다. |

## M4: 단일 장애 사례부터 검증

1. 서비스·환경·계정·리전과 원인을 알고 재현 가능한 장애 하나를 정한다. 실험 시작·종료 시각, 주입 방법, 실제 원인을 AI 보고서와 분리해 기록한다. 실제 Alarm→Incident로 접수된 **대표 Incident ID**를 분석 대상으로 사용한다.
2. 같은 대상의 UTC 시각 범위에서 로그·메트릭을 사람이 먼저 조회해 원본 위치·조회 조건·단위·집계를 기록한다. 배포 버전과 Trace는 실제 수집돼 연결이 확인된 경우에만 사용한다.
3. AI를 붙이기 전 읽기 전용 MCP Tool의 허용 대상, 결과 수·시간 범위·호출 횟수·시간·비용 상한과 `성공/데이터 없음/일부 결과/권한 없음/시간 초과/실패` 구분을 시험한다. Tool이 복구 Action을 호출할 수 없어야 한다.
4. 비동기 분석 결과에서 **관측된 사실·원인 가설·반대 근거·미확인 항목·권장 다음 조회**를 분리한다. 사실에는 재조회 가능한 원본 참조와 대상·시각·조회 조건을 붙인다. 실제 주입 원인과 보고서를 사람이 비교하고, Tool 실행 성공과 원인 판단 정확도를 따로 평가한다.
5. 같은 장애에 대해 로그 누락, 조회 실패, 권한 거부, 시간 초과, 서로 어긋나는 로그·메트릭을 각각 시험한다. 자료가 없거나 충돌하면 원인을 확정하거나 정상 상태로 판정하지 않고 부족한 근거와 다음 확인 방법을 표시한다. 재시도는 승인된 횟수·비용 안에서만 일어나야 한다.

6. [M4 API 초안](../contracts/rca-analysis.md)의 같은 키 재전송·본문 충돌·진행 중 중복·내부 재전달·lease 재획득·취소/완료 경합·보고서 발행 실패를 검증한다. 실행/보고서/근거의 대표 Incident 연결, 종료 상태와 보고서 유무, 호출·비용 누적 기록을 대조한다.

첫 사례 통과를 M4 전체 완료로 표시하지 않는다. 이후 앱·인프라·DB 장애를 **각각 근거와 함께 분류할 수 있는지** 실제 주입 원인과 비교한다. 사례 수, 허용 오판 기준, 분석당 비용·시간 상한은 첫 시험 전에 확정한다. 보고서 저장·조회 구조와 모델·Tool 버전 기록도 별도 계약으로 확정한다.

## M5: 승인과 복구를 별개 결과로 검증

1. M4의 근거 있는 보고서와 되돌릴 수 있는 시험 환경 작업 **한 가지**를 선택한다. 제안에는 정확한 계정·리전·환경·서비스·리소스, 현재/목표 상태, 작업 인자, 예상 영향과 만료 시각을 고정한다. 대상과 정상 판정 기준은 실행 전에 확정한다.
2. 사용자가 제안을 검토해 승인하거나 거절한다. 서버는 실제 검증된 JWT와 변경 권한, 승인자, 저장된 제안 버전·대상·작업·만료·중복 사용 여부를 다시 확인한다. 프런트의 버튼 상태나 클라이언트가 보내는 변경 인자만으로 실행하지 않는다.
3. 미승인, 거절, 만료, 권한 없음, 다른 사용자, 바뀐 대상·인자, 중복 승인, 반복/동시 실행 요청을 각각 거부하거나 **한 번의 작업**으로 수렴시키는지 시험한다. 승인 선점과 실행 기록은 원자적으로 남긴다. 외부 Action과 DB 쓰기는 하나의 트랜잭션이 아니므로 DB 선점만으로 외부 효과 1회를 보장했다고 표시하지 않는다.
4. 허용 목록에 있는 MCP Action Tool만 대상 리소스에 한정된 변경 권한으로 호출한다. 읽기 Role과 Action Role을 분리한다. Action 실패·부분 실패·시간 초과·결과 미확인 시 추가 실행을 무한 재시도하지 않고 중단·수동 확인 상태를 표시한다.
5. 실행 API의 성공과 서비스 복구를 별도로 확인한다. 배포 상태, Health Check, 실제 API 요청·지표 중 선택한 기준을 사후에 측정한다. Alarm `OK`만으로 복구 완료 또는 Incident `Resolved`를 표시하지 않는다. 승인·거절·실행·실패·확인 결과와 근거를 감사 기록으로 남기되 JWT·토큰·비밀값은 남기지 않는다.

6. [M5 재개 초안](../contracts/recovery-approval.md)에 따라 Action 직전/수락 직후 종료·응답 유실·DB 결과 저장 실패·lease 만료/동시 재전달을 시험한다. 대상 멱등 키의 실제 효과 수·보존 기간을 확인하고, 지원이 없거나 결과가 불명확하면 자동 재전송 대신 `action_unknown`·결과 대조·새 제안/승인에 따른 수동 재개로 처리한다.

M5의 통과 조건은 위 긍정·거절·실패 사례의 실제 시험 기록과 사용자 화면에서의 결과 확인이다. 첫 Action, 승인 권한 모델, 만료 기간, 원자적 멱등 키, 실패 시 중단 정책, 서비스 회복 임계값은 **사용자 결정 또는 별도 계약 승인 전**에는 확정값처럼 쓰지 않는다. 운영 환경 자동 실행은 첫 시험 범위가 아니다.

## 증거 기록 형식

각 시험에 날짜·계정·리전·서비스·환경, 코드 커밋과 배포 버전, 입력·기대 결과·실제 결과, Incident/분석/승인/실행 ID, 로그·메트릭·배포·API 응답의 재조회 경로, Tool·모델 버전, 실행 시간·호출량·비용, 실패와 미확인 범위를 남긴다. 비밀값과 개인 정보는 제외한다. CI·로컬 테스트·AWS 실제 동작을 따로 표시하고, 마일스톤 상태는 기존 Notion 보드에서 근거와 함께 갱신한다.
