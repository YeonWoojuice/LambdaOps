# M5 복구 제안·승인·실행 계약 — 제안 / 사용자 검토 전

상태: **설계 초안, 사용자 승인 전. M5 승인 API·MCP Action Tool·감사 저장 구조는 아직 구현·배포되지 않았다.** 사용자가 확정한 [목표 아키텍처](../architecture/overview.md)의 **권장 → 사용자 승인 → Action Tool 실행 → 실제 서비스 확인** 순서를 구체화한다. [M4 RCA 초안](rca-analysis.md)의 보고서는 판단 자료일 뿐 승인이나 실행 명령이 아니다. 기존 [M3 Incident API](incident-api.md)의 `page/pageSize` 목록·상세 응답과 [Alarm 에피소드 계약](alarm-event.md)은 변경하지 않는다.

## 경계와 선행 조건

- 첫 적용은 **개발/시험 환경의 안전하게 되돌릴 수 있는 작업 한 가지**로 한정한다. 실제 배포 방식과 이전 버전을 확인하기 전에는 Rollback을 확정 작업으로 부르지 않는다. M4의 근거 있는 `reportId`를 연결하되, 근거 부족 보고서의 실행 가능 여부는 별도로 결정한다.
- Backend는 요청된 이전 Incident ID를 [M3 상세 계약](incident-api.md)의 현재 대표 `incidentId`로 해석한다. 제안·승인·실행 기록은 대표 ID와 최초 요청 ID를 구분한다. 서로 다른 Alarm 에피소드를 하나의 복구 승인으로 임의 병합하지 않는다.
- `alarmState=OK`는 Alarm 에피소드 종료일 뿐 서비스 복구 증거가 아니다. 현재 DSQL의 `incident_state`는 `NEW`만 허용하므로 M5 상태를 기존 필드에 임의로 기록하거나 `Resolved`로 바꾸지 않는다.

## 복구 제안: 변경할 수 없는 승인 대상

서버가 허용 목록의 Action 종류와 실제 대상 정보를 확인한 뒤 `pending_approval` 제안을 발급한다. AI가 만든 자유 텍스트를 그대로 실행 인자로 사용하지 않는다. 다음 값은 승인 후 변경할 수 없으며 바뀌면 **새 제안 ID·버전과 새 승인**이 필요하다.

| 필드 | 의미와 검증 |
| --- | --- |
| `proposalId`, `proposalVersion`, `proposalHash` | 승인 대상의 고유 ID·버전·서버가 정규화한 내용의 해시. 같은 제안의 내용 바꿔치기를 거부한다. |
| `incidentId`, `reportId` | 대표 Incident와 근거 RCA. 보고서 버전과 상태를 함께 기록한다. |
| `target` | 계정·리전·서비스·환경·리소스 ARN/ID를 정확히 지정한다. 서버의 Incident 문맥·허용 목록과 일치해야 한다. |
| `actionType`, `parameters` | 허용된 단일 Action과 검증된 인자. 임의 shell 명령·임의 대상 문자열은 허용하지 않는다. |
| `expectedState`, `desiredState` | 실행 전 다시 확인할 실제 배포/리소스 버전과 의도한 결과. 확인되지 않은 이전 버전은 제안하지 않는다. |
| `risk`, `impact`, `rollbackPlan` | 사용자에게 보여줄 예상 영향·중단 조건·수동 되돌림 방법. |
| `createdAt`, `expiresAt` | UTC RFC 3339 시각. 서버 시각이 만료 이후면 승인·실행을 거부한다. |

이 초안의 **승인 후 내부 실행 방식**을 채택한다면, 화면은 위 대상·작업·현재/목표 상태·만료·위험을 승인 버튼 옆에 표시하고 **“승인하면 이 작업의 실행이 요청됨”**을 명확히 알린다. 별도 실행 확인 단계를 채택할지는 사용자 결정이다. 프런트는 제안을 읽어 보여줄 뿐 Action Tool을 직접 호출하지 않는다.

## 제안 API — 구현 전 확정할 HTTP 형태

| 경로 | 권한·동작 | 성공 응답 후보 |
| --- | --- | --- |
| `GET /incidents/{incidentId}/recovery-proposals/{proposalId}` | 인증된 조회 권한으로 제안·상태·감사 가능한 결과를 읽는다. 이전 Incident ID는 대표로 정규화한다. | `200` 제안, 현재 상태, 실행/확인 결과. `Cache-Control: no-store`. |
| `POST /incidents/{incidentId}/recovery-proposals/{proposalId}/decisions` | 별도 **복구 승인 권한**으로 `approve` 또는 `reject`를 제출한다. 서버가 JWT·제안·대상·만료·중복 사용을 재검증한다. | 승인: `202`와 같은 `proposalId`·`executionId`·`approved`/`queued` 상태. 거절: `200`과 `rejected`. |

결정 요청 본문의 후보는 `{ "decision": "approve", "proposalVersion": 1, "idempotencyKey": "client-generated-opaque-id" }`다. 본문에 Action 종류·ARN·명령 인자를 다시 받지 않는다. 키는 서버가 사용자·제안 ID·버전·결정과 결합한다. 동일 사용자의 동일 키 재전송은 **같은 결정과 실행 ID**를 반환하고, 이미 거절·만료·소비된 제안에 다른 키로 새 승인을 만들지 않는다. 실제 상태 코드·키 형식·만료 시간은 사용자 검토 후 확정한다. 공개 브라우저용 `execute` API는 두지 않고, 승인 기록의 커밋 후 내부 작업이 실행을 한 번 선점하는 방식을 제안한다.

## 상태와 서버 재검증

| 대상 | 상태 후보 | 전이 규칙 |
| --- | --- | --- |
| 제안 | `pending_approval → approved` 또는 `rejected` / `expired` / `invalidated` | 승인·거절은 한 번만 확정한다. 대상/버전 변경, 만료, 권한 변경을 확인하면 이전 제안을 실행하지 않는다. |
| 실행 | `queued → executing → action_succeeded` / `action_failed` / `action_unknown` | 승인된 제안당 실행 ID 하나를 원자적으로 선점한다. 타임아웃으로 결과가 불명확하면 재실행 전에 실제 리소스 상태를 조사한다. |
| 서비스 확인 | `pending → recovered` / `not_recovered` / `inconclusive` | Action API 결과와 별도로 대상 배포·Health Check·실제 API 요청·지표의 승인된 기준을 확인한다. |

승인 시 Backend는 **검증된 JWT의 사용자 식별자와 별도 변경 scope**, 이 사용자의 승인 허용 여부, 제안의 대표 Incident·`reportId`·해시/버전, 정확한 대상·작업, 만료, 아직 미사용 상태를 확인한다. 현재 M3의 읽기 scope만으로 변경 권한을 주지 않는다. 실행 직전에도 서버가 저장한 승인과 대상의 실제 `expectedState`를 재검사한다. 프런트의 버튼 상태, Agent 텍스트, 클라이언트가 재전송한 대상은 권한 근거가 아니다.

상태 전이는 DSQL의 짧은 원자적 트랜잭션과 고유 제약/조건부 갱신으로 **승인 1회·실행 선점 1회**를 보장하도록 설계한다. 네트워크 재전달·동시 클릭·작업자 재시작에서도 같은 승인으로 두 번째 Action이 나가지 않아야 한다. Action의 결과를 알 수 없는 경우 `action_unknown`으로 남겨 자동 반복을 중단하고 수동 대조한다. M3의 세 테이블이나 에피소드 계산을 이 요구 때문에 변경하지 않는다.

## Action Tool과 사후 확인

Action Tool은 서버가 확인한 `executionId`만 받아 저장된 **불변 제안**을 조회하고, 대상 계정·리전·환경·리소스와 작업 인자를 다시 검증한다. 모델이 직접 Action Tool을 호출하거나 임의 명령을 주입하지 못한다. 읽기 도구 역할과 분리된 최소 IAM/외부 권한을 사용하며, 첫 환경·작업·리소스만 허용한다. 거부·실패·부분 실패·시간 초과는 각각 기록하고 무한 재시도하지 않는다.

검증 작업은 실행 결과와 **서비스가 실제 회복했는지**를 별도 필드로 기록한다. 실행 전·후의 배포 상태/버전, Health Check, 실제 요청 응답, 선택한 지표의 시간 창과 기준값을 비교한다. 필요한 표본 수·관측 기간·정상 기준은 첫 Action을 정할 때 확정한다. `OK`만 발생했거나 검증 데이터가 없으면 `recovered`가 아니다. 실패·부분 성공·미확인은 사용자 화면에 구분해 보여준다.

## 감사 기록과 DSQL 확장 결정

제안 생성, 사용자 승인/거절, 서버의 허용/거부 이유, 실행 선점·Tool 호출·결과, 사후 확인과 수동 조치를 **시간순 변경 불가능한 감사 사건**으로 남긴다. 각 사건에는 대표 Incident ID, 제안/보고서/실행 ID, 사용자 `sub` 또는 서버 작업자 ID, 대상 해시/식별자, UTC 시각, 결과 코드, 재조회 가능한 근거 참조를 둔다. JWT 원문, 비밀번호, DB 토큰, 민감 로그 전문은 저장하지 않는다. 감사 조회 권한과 보존 기간은 별도 확정한다.

현재 승인된 DSQL은 M3의 `alarms`·`alarm_events`·`incidents` **3개 테이블**이다. M5의 제안·결정·실행·확인·감사 데이터는 별도 확장 스키마가 필요하지만, 이 초안은 SQL/마이그레이션을 작성하거나 기존 제약을 변경하지 않는다. 새 테이블 수, 고유 키·외래키·원자적 선점 방식, M4 보고서와의 연결, 보존 기간·비용은 [Incident DB ADR](../decisions/0001-incident-db.md)을 검토한 뒤 사용자 승인으로 확정한다.

## 오류·검증 게이트와 미결정

인증 없음 `401`, 변경 권한 없음 `403`, 대상 없음 `404`, 만료·제안 버전 불일치·이미 소비됨 `409` 등의 응답 후보를 둔다. 내부 권한·비밀값·실행 명령 전문은 오류 본문에 노출하지 않는다. 정확한 오류 코드·재시도 정책은 구현 계약 확정 시 정한다. [M4·M5 검증 게이트 초안](../testing/m4-m5-verification.md)의 미승인·만료·대상 변경·중복·동시·Action 실패·서비스 확인 실패를 실제 환경에서 통과해야 한다.

**사용자 결정 전:** 첫 Action과 실행 환경, 승인 가능한 사용자·scope, 승인 뒤 즉시 내부 실행할지 별도 실행 단계가 필요한지, 만료 시간, 재실행 허용 정책, 서비스 회복 기준, 감사 보존 기간과 DSQL 확장 모델을 확정해야 한다. PR 병합이나 설계 승인은 AWS 배포·복구 실행 승인이 아니다.
